## In-app products

Three plans, all real, shown one above the other: 1 month, 3 months, and Forever, which is the
lifetime pass. The pass is the one the app argues for, on the honest ground that it costs less than
three months of the monthly plan. The app works that out from the prices Play actually charges, so
it stays true in every country whatever Play's conversion comes to, and there is no invented "was"
price anywhere, which Play rejects anyway.

**Lifetime pass ("Forever" in the app)** — Monetisation → In-app products:

| Field | Value |
| --- | --- |
| Product ID | `zenith_plus` (cannot be changed once created) |
| Type | One-time product, non-consumable, "multi-quantity" off |
| Name | Zenith Plus — Lifetime |
| Description | Hidden apps, backup & restore, the island and more. Paid once, yours for good. |
| Price | $10.00 (Play converts for other countries) |

**Subscription** — Monetisation → Subscriptions. One subscription with two base plans. A purchase of
either is the same product, so either one counts as subscribed. The app finds each plan by how often
it bills, every month or every 3 months, so the base plans' IDs and their order make no difference
to it.

| Field | Value |
| --- | --- |
| Subscription ID | `zenith_plus_monthly` (named before it had a second plan; an ID cannot be changed) |
| Name | Zenith Plus (Play's purchase sheet shows it, so no longer "Monthly") |
| Base plan: monthly | Auto-renewing, billed every month, $4.00. It keeps whatever ID it already has |
| Offer on the monthly plan | Free trial, 7 days, new subscribers |
| Base plan: `three-months` | Auto-renewing, billed every 3 months, $8.00, no offer |

Create all of it and **activate** the pass and both base plans. Once Play has the subscription, the
app shows only the base plans it carries: until `three-months` is active the sheet offers 1 month
and Forever, and the 3 months card appears by itself once it is, with no new build.

To add the 3 month plan: open `zenith_plus_monthly`, **Add base plan**, base plan ID
`three-months`, type Auto-renewing, billing period Every 3 months. Under prices, set $8.00 for the
United States and let Play convert it for the other countries, then **Save** and **Activate**.
Do this, and the new prices, only once the first build with three plans is on the track testers
install from: an older build sells whichever plan Play lists first as its Monthly, which could be
this one, and says the pass costs about eight months of the monthly.

To move the monthly plan to $4: open its base plan, edit its prices to $4.00, converted for the
other countries the same way, and **Save**. If Play asks what to do for people already subscribed,
leaving them on the price they signed up at is fine. Its 7 day free trial offer stays as it is.

The seven day trial is offered on the last screen of setup and counted by the app itself, from the
moment it is accepted. It needs nothing configured in Play. Create the one-time product and activate
it *before* the first release goes to testers, or the buy button will correctly say the purchase is
unavailable.

### Who counts the free week

Once the monthly base plan of `zenith_plus_monthly` carries its 7 day offer, "Start my free days"
hands over to Play's own sheet — the familiar "7 days free, then $4.00 a month" one — and Google
counts the week and takes over billing at the end. Only an offer on the monthly plan counts, since
the app says the monthly price follows the trial. Until that offer exists, the app counts the seven
days itself and asks for nothing, which is what happens today. Same button either way; no new build
needed to switch.

To test the purchase without paying: Play Console → Setup → License testing, add the tester's Gmail
address, then buy from a build signed with the upload key and installed from a Play track.

## Data safety form answers

For a build with a server. (A build without one collects nothing: the answers before 2026-10-04 in
this file's history.)

- **Does your app collect or share any of the required user data types?** Yes, collects. Nothing is
  shared with third parties.
- **Is all of the user data collected by your app encrypted in transit?** Yes (HTTPS only; the
  release build refuses to talk to an address that is not HTTPS).
- **Do you provide a way for users to request that their data is deleted?** Yes: in the app
  (Settings > Account > Delete account) and on the web page below.
- **Account creation:** the app lets people create an account: "Username and password" and "OAuth"
  (Google). **Delete account URL:** `https://zenithlabz.duckdns.org/delete-account` (the page the
  server itself serves).

Data types, each **collected, not shared, optional** (only if the person makes an account, and for
the last three only if they also send a backup or share a Look), purpose **App functionality** (and
**Account management** for the first two). A shared Look is opened only by people the sharer gives
its code to, which they expect, so it is not "shared" in the form's sense; the Featured list holds
only Looks the developer picked:

| Data type | What it is here | Notes |
| --- | --- | --- |
| Personal info → User IDs | The username, or Google's number for the Google account | |
| Personal info → Email address | Inside Google's sign-in token, with Continue with Google | Tick "processed ephemerally": the server checks the token and keeps only the number |
| Personal info → Name | The name typed during setup, inside a backup | Only in a backup. Google's token also carries a name, read and not kept |
| App activity → Installed apps | The apps placed on the home screen and the apps hidden, inside a backup; the apps placed on the home screen, inside a shared Look | Never the whole list of installed apps |
| App activity → Other user-generated content | The Quick Note widget's text, inside a backup; the name given to a shared Look | |

Not collected: location, contacts, photos, files, messages, device IDs, diagnostics, and anything
financial. The Zenith Plus purchase is handled entirely by Google Play; the server is told nothing
about it, and a backup sent to the account leaves the purchase and the trial out.

Note for the reviewer, if asked: the launcher reads the list of installed applications through
`LauncherApps` in order to display them, and — only with the user's consent — today's calendar
entries for the Calendar widget and the bedside clock. The calendar entries are never transmitted, logged or stored
off-device. Nor is the list of installed applications as a whole; a backup the user chooses to send
to their account names the apps on their home screen and the ones they hid, which is what "Installed
apps" above declares.

## App access

Tick "All functionality is available without special access": an account is optional, anyone can
make one in the app (Settings > Account) with any username and a password, and no code or invitation
is needed. Backing up to the account needs Zenith Plus, which the seven free days unlock.

## Permissions declared

| Permission | Why |
| --- | --- |
| `SET_WALLPAPER` | Zenith sets the wallpapers it paints, and a photo you pick in it |
| `VIBRATE` | A short tick when you pick up an icon or resize a widget |
| `READ_CALENDAR` | Optional. Requested at runtime the first time you tap "Show your events" on the Calendar widget or ask the bedside clock to show today's events; the launcher works fully without it |
| `com.android.vending.BILLING` | Selling Zenith Plus through Google Play |
| `INTERNET`, `ACCESS_NETWORK_STATE` | `INTERNET` is the app's own since 2026-10-04: it reaches Zenith's server once somebody makes or signs in to an account, and never before, and Open-Meteo once a place is chosen for the Weather widget. Both are also merged in by the Play Billing library so it can reach Google Play |

`READ_CALENDAR` is in the "personal and sensitive" family, so the listing must explain it: the Calendar widget lists today's events and the bedside clock shows them on a dimmed screen, the data is read on the device and never leaves it, and every other feature works if you decline.

No `QUERY_ALL_PACKAGES`: app discovery uses `LauncherApps` plus a `<queries>` element, so no sensitive-permission declaration form is required.
